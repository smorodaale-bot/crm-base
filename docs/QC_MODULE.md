# Модуль контроля качества менеджеров (Кандидат 3)

Работающий модуль внутри CRM: приём транскрибации (или аудио + текст), автоматическая оценка разговора, ручная корректировка и отчёт руководителя.

## Стек

- **Backend:** Node.js, Express.js REST API
- **DB:** PostgreSQL + Prisma (`QcReview`, `QcComment`)
- **Frontend:** React (страницы `/qc`, `/qc/:id`, `/qc/report`)
- **Анализ:** детерминированный rules-движок `rules-v1` (+ опционально OpenAI)

## Быстрый старт

```bash
npm run install:all
cd backend
npx prisma migrate deploy
npm run db:seed
cd ..
npm run dev
```

Войти как руководитель: `boss@crm.local` / `Password123!`  
Открыть **Контроль качества** в боковом меню.

Seed загружает **5 тестовых разговоров** с готовыми оценками.

## Система оценки

### Положительные критерии (веса → вклад в 0–100)

| Критерий | Вес | Что ищем |
|----------|-----|----------|
| Представился | 10% | имя, компания, должность |
| Выявил потребность | 15% | цели, задачи, сценарий |
| Выявил бюджет | 10% | бюджет / ценовой диапазон |
| Выявил сроки | 10% | когда нужна покупка |
| Презентовал продукт | 15% | модель, выгоды, опции |
| Отработал возражения | 15% | принятие + аргумент / альтернатива |
| Согласовал следующий шаг | 15% | дата/канал/действие |

`positiveScore = Σ (score_i / 100 × weight_i) × 100`

### Негативные критерии (штрафы)

| Критерий | Макс. штраф | Критичность при балле |
|----------|-------------|------------------------|
| Недостоверные обещания | −25 | ≥ 70 |
| Грубость | −30 | ≥ 60 |
| Некорректность | −20 | ≥ 70 |
| Признаки конфликта | −25 | ≥ 60 |

`overall = clamp(0..100, positiveScore − penalties)`

Разговор **критический**, если `overall < 40` или сработал порог негативного критерия / severity=`critical`.

### Доказательства

Для каждого критерия движок сохраняет **фрагменты реплик** из транскрипта (поле `evidence`), по которым можно проверить вывод вручную.

## REST API

Базовый префикс: `/api/qc` (JWT обязателен).

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/criteria` | Справочник критериев |
| GET | `/reviews` | Список проверок (`?critical=true&q=`) |
| POST | `/reviews` | Создать: JSON или `multipart` (`transcript`, опц. `audio`) |
| GET | `/reviews/:id` | Деталь + транскрипт + evidence |
| PATCH | `/reviews/:id` | `manualScore`, `supervisorComment`, `comment` |
| GET | `/report` | Отчёт руководителя (только SUPERVISOR/ADMIN) |
| POST | `/analyze-preview` | Прогон анализа без записи в БД |
| GET | `/fixtures` | Эталонные диалоги (руководитель) |

Пример создания:

```bash
curl -X POST http://localhost:4000/api/qc/reviews \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d "{\"title\":\"Тест\",\"managerId\":3,\"transcript\":\"Менеджер: Меня зовут Анна...\"}"
```

Аудио: поле `audio` + желательно `transcript`. Без `OPENAI_API_KEY` авто-Whisper недоступен — текст обязателен.

Опционально: `OPENAI_API_KEY` и `useLlm=true` — доп. резюме/рекомендации через LLM (баллы остаются на rules-движке для воспроизводимости).

## Как проверялось качество выводов

1. **Golden set из 5 диалогов** (`backend/src/qc/fixtures.js`) с заранее заданными ожиданиями:
   - диапазон overall;
   - mustPass / mustFail;
   - mustBeHigh / mustBeLow для рисков;
   - флаг `isCritical`.
2. **Автотест** `backend/tests/qc.test.js`:
   ```bash
   cd backend && npm test
   ```
   Проверяет, что анализатор попадает в ожидания и что evidence берётся из текста транскрипта.
3. **Ручная валидация:** в UI открыть проверку → сверить фрагменты «evidence» с транскриптом → при необходимости скорректировать оценку и оставить комментарий руководителя.
4. **Отчёт:** средние по менеджерам, частые ошибки, динамика по дням, отдельный список критических.

Итог: выводы не «чёрный ящик» — у каждого критерия есть цитата; регрессии ловятся golden-set тестом.

## Тестовые разговоры (seed)

1. Идеальный звонок — кроссовер (высокий балл)
2. Слабая квалификация — сразу в презентацию
3. Грубость и конфликт (критично)
4. Недостоверные обещания и давление (критично)
5. Хороший звонок с отработкой «дорого»
